# 代码来源核查与第三方声明

## 为什么先做这个

同源率是一个读数，审查方真正要回答的问题是："这份代码里，哪些是你们自己写的，哪些来自开源？" 这两类东西的处理方式完全相反：

- **自研代码**被误判 → 用 `reduce-code-similarity-by-refactor` 真实重构 + 用 git 历史作为原创证据
- **上游派生的配置/规则/看板** → 声明出处，保留许可证义务；给它加"自研"标记是这份材料里唯一会变成假话的地方

先分类，再动手；否则会出现"上游文件加了自研标记、自研代码却被当成可疑"的错位。

## 判定方法（按可信度排序）

1. **文件内证据（最硬）**：上游项目 URL、版权头、`SPDX-License-Identifier`、原版注释、上游特有的键名或默认值。
   例：`falco/falco.yaml` 中残留的 `github.com/falcosecurity/...` 注释，可确认整份文件是上游默认配置。
2. **文件形态证据**：整份拷贝的上游默认配置（上千行、每个选项都带注释、含大量本项目未使用的键）；社区看板 JSON；示例规则集。
3. **历史证据**：`git log --diff-filter=A -- <file>` 首次提交是否与主体开发同期、是否为一次性批量加入；`git log -p` 里是否有"从上游复制/参考"的描述。
4. **文本证据**：与上游同版本文件做逐段比对（`diff`、或按函数级别的相似度工具）。这是判定"疑似逐字片段"的唯一可靠手段。

判定注意事项：

- **AI 助手生成的代码可能与训练语料中的开源实现逐字接近**。这与"作者是否主观抄袭"无关，但同样触发署名义务——必须按逐字片段处理。
- 不要凭"名字像"下结论。仓库里存在与开源项目同名的目录，不等于该目录来自那个项目。

## 产出物

### 1. 来源清单 `.dsh/audit/provenance-inventory.md`

逐文件一行，至少包含：

| 字段 | 说明 |
|---|---|
| 文件 | 相对路径 |
| 类别 | 自研 / 上游派生（配置·规则·看板）/ 疑似逐字片段 / 第三方依赖 |
| 依据 | 判定证据（文件内 URL、首次提交、比对上游客体） |
| 处理 | 无需处理 / 重构 / 声明出处 / 署名或重写 |

### 2. `THIRD_PARTY_NOTICES.md`（仓库根目录）

对每个上游派生文件或组件写明：组件名、来源 URL、版本或抓取时间、许可证、本项目如何使用（裁剪/修改/直接引用）、以及被修改的说明。

### 3. `LICENSE`（若缺失）

仓库没有 `LICENSE` 时，首版次材料里"自主知识产权"的主张是没有落脚点的。**不要替用户选许可证**：把这一点作为待决事项列出（含专有/闭源与开源两种走向的后果），由用户或法务决定。可以先行准备 SPDX 头模板供选定后批量添加。

## 执行步骤

1. 枚举纳入审查范围的文件（源码 + 配置 + 规则 + 看板 + Docker/compose），排除 `node_modules`、`uv.lock`、`package-lock.json`、`.git`。
2. 对每个文件跑上面 4 类证据检查，填清单。
3. 对"疑似逐字片段"逐个与上游客体比对，记录命中位置（文件 + 行范围 + 上游 URL）。
4. 生成 / 更新 `THIRD_PARTY_NOTICES.md`。
5. 检查是否有被误加的自研标记（例如 `@mx`、`@MX`、`[Mx]`、`由…研发` 注释）落在上游派生文件上；若有，**移除该标记**，改为出处说明。
6. 汇总待决事项（许可证选择、逐字片段的重写或署名、需要业务方确认的第三方组件清单），交给用户。

## 与审查方的沟通口径

- 主动列出第三方组件与许可证，比等审查方发现更有利：首版次审查在意的是"是否如实披露"，不是"是否用了开源"。
- 自研部分用**可核查的证据**说明：模块级首次提交时间、提交作者、逐功能演进历史、设计文档。不要生成无法验证的材料（补造的开发记录、回填的提交时间）——那会把一个可以解释的技术问题变成材料造假。
- 如果比对工具把通用范式判为同源，如实说明判定口径（工具按函数/片段粒度、不做标识符归一化），并附上重构后的比对结果。
