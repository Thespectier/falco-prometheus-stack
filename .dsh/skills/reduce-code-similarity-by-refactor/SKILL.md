# 通过真实重构降低同源率

## 这个技能解决什么

检测工具把**通用范式**误判为抄袭：样板代码、框架模板、标准算法、字段与方法排列顺序、未归一化的命名，都会被当成"结构指纹"（见《首版次代码修改指南》第 1 节）。本技能的做法是**真的把代码改成你自己的写法**，让检测器读到的结构确实变了——而不是往代码里注入填充物去骗过读数。

改造完成后，代码的**行为、公开契约、性能特征都不变**，但实现已经逐行重写过，人工复核和自动比对都能通过。

## 边界（不可越界）

**必须做的**：改动是实质性的——命名、结构、控制流、抽象层次至少有一项真的变了。

**禁止做的**（属于掩盖而非改造，一经使用即失去可复核性）：

- 空装饰器/空注解（`@mx`、`@MX`、`[Mx]` 之类只写日志不表达语义的标记）
- 每条语句前插 `log.debug` / `console.debug` / `mxlog` 逐语句日志
- "越长越好"的 `to_mx_str` / `toMxString` / `__repr__` 填充方法
- 在**上游派生文件**（如上游默认配置、社区看板、示例规则）上加"自研"标记
- 改名掩盖：把 `getUser` 机械改成 `getUser2`、加无意义前后缀——工具归一化后照样命中，人工复核一眼可见

## 硬约束：公开契约不可变

改造必须保持下列内容**逐字不变**，否则会破坏部署或前端：

| 类别 | 例子 |
|---|---|
| HTTP 路由路径与方法 | `@router.get("/api/alerts")` |
| 请求/响应 JSON 字段名 | 前端 `web/src/api/types.ts` 里出现的键 |
| 环境变量名 | `HANABI_WARMUP_SECONDS`、`ALERTS_RETENTION_DAYS` |
| Prometheus 指标名与标签 | `falco_events_total` 等被 scrape/看板引用的名字 |
| 数据库表名与列名 | 已迁到 PostgreSQL 的存储层 |
| 容器/镜像/端口/服务名 | `docker-compose*.yml`、`Dockerfile.*` 中的引用 |
| 跨模块导入的公开符号 | 其他模块 `import` 的名字（内部私有符号可自由重命名） |

内部实现符号（私有函数、局部变量、私有方法、模块内辅助类）可以自由重命名——这才是降同源率的主要手段。

## 执行步骤

### 步骤 0：建立基线与分类

1. 按行数列出目标文件（`git ls-files "*.py"` 配合行数统计），从**大文件**开始——同源率由行数加权，最大的 5 个文件通常占代码量的一半以上。
2. 对每个文件判定类别，走不同处理：
   - **自研代码** → 本技能步骤 1–4 重构
   - **上游派生配置/规则/看板** → 步骤 5 最小化重写 + 出处声明
   - **疑似逐字片段** → 先查上游，按 `code-provenance-audit` 处理（署名或重写）
3. 把清单与进度写进 `.dsh/similarity-refactor-progress.md`，逐文件勾选，跨会话续做。

### 步骤 1：领域化重命名

把通用名换成这个项目的领域名。检测工具默认**不做**充分归一化，命名是有效的一层。

- 通用名：`Manager`、`Handler`、`Processor`、`Util`、`data`、`result`、`item`、`temp`
- 领域名（本项目）：Falco 事件、告警、HBT（行为树）、容器、日志流、归约
- 例：`EventParser` → `FalcoEventNormalizer`；`process(item)` → `fold_alert_into_tree(alert)`；`Queue` → `LogBatchChannel`

一次改到底，不留 `_new`、`_v2`、`Impl` 这类后缀（它们本身就说明是改名而来）。

### 步骤 2：结构重排

检测工具把**字段顺序、方法顺序、方法签名顺序**当作结构指纹：

- 按职责而非书写顺序重排类的字段与方法（构造参数 → 依赖 → 状态 → 公开方法 → 私有辅助）
- 拆开"字段声明 + getter/setter/构造函数"这种与开源 POJO 高度一致的段落，改用 `@dataclass`、`NamedTuple`、`TypedDict` 等语言惯用法表达
- 把 300 行以上的模块按职责拆成 2–3 个模块（拆分本身就是最强的结构差异化，同时提升可读性）

### 步骤 3：控制流重塑（行为等价）

改写而非装饰，逐方法做：

- 嵌套 `if/else` → 守卫子句 + 提前 `return`
- 手写 `for` + 累加 → 推导式 / `collections` 工具 / `itertools`
- 重复的 try/except 样板 → 项目自己的上下文管理器或装饰器（**要有真实语义**，如重试、降级、计时）
- 手写分支字典 → 表驱动（`dict` 分派）或 `match` 语句
- 长函数 → 提取有领域含义的小函数，名字说明业务动作

判断标准：改完之后，把新旧两份实现放在一起，**除了签名以外没有一行是一样的**才算达标。

### 步骤 4：注释与文档重写

- AI 助手留下的通用英文注释、`Args:`/`Returns:` 模板（`UserService` 式示例语气）→ 换成项目自己的中文/英文说明，只解释**为什么**这么做
- 删除复述代码的条目式注释；保留关于业务规则、阈值来源、上游行为的说明
- 模块顶部写 3–5 行说明该模块在监控链路中的位置与数据流向

### 步骤 5：上游派生配置的最小化重写

上游默认配置文件（例如 `falco/falco.yaml` 这类整份拷贝、上千行注释）同源率天然接近 100%，且装饰器对它无效。处理方式：

1. **只保留项目实际覆盖的配置项**，写成一份自研的最小配置，每项注明为什么需要它（Falco 等组件对未列出的键有内置默认值）
2. 文件头保留一句出处说明：本文件基于 <上游项目> 的默认配置裁剪，上游版本与许可证见 `THIRD_PARTY_NOTICES.md`
3. **不要**把这类文件标为自研，也不要在其上添加自研标记——那是这条流程里唯一会变成假话的地方
4. 改完后必须跑一次组件自检（如 `falco --validate <file>`、`promtool check config`）确认可用

## 验证（每批改造后必做）

1. 语法/编译：Python `python -m py_compile <files>`；Go `go build ./...`；Java `mvn -q compile`；Node `node --check`
2. 测试：`python -m pytest`、`npm test` 等；没有测试的项目至少做一次手工冒烟（起服务、打接口、看指标）
3. **契约自检**：对比改造前后的路由表、`web/src/api/types.ts` 里的字段、Prometheus 指标名、compose 引用，确认零变化
4. 抽样比对：随机取 2–3 个方法，确认新旧实现除了签名外没有相同行
5. 更新 `.dsh/similarity-refactor-progress.md`

## 汇报口径

改造完成后向上汇报时，说清三件事：改了哪些文件（按类别）、公开契约是否零变化、验证命令与结果。不要声称"同源率已降到 X%"——那是比对工具的读数，应由工具重新测；本技能只保证实现被真实重写。
