# 原创性证据包（基于 git 历史）

## 原则

只做**可核查事实的整理**，不做材料的加工：

- ✅ 从 `git log` 提取客观事实：提交时间、作者、文件首次出现的提交、变更规模
- ❌ 不补造开发记录、不回填/修改提交时间、不生成没有出处的"设计文档"、"会议记录"
- 如果历史里有不利于说明的内容（例如一次性导入的上游文件），如实列出并在说明中给出解释口径，而不是从材料里删掉——审查方拿到仓库就能看到，隐瞒的代价远大于解释

## 产出物：`docs/independent-development-statement.md`（或用户指定路径）

### 1. 项目概览与时间线

```bash
git log --reverse --date=short --pretty=format:'%ad %h %an %s' | head -50
git rev-list --count HEAD
git shortlog -sne HEAD
```

整理成：起始提交日期 → 首个可用版本 → 关键功能里程碑（按提交主题聚类）→ 当前状态；附提交总数与作者分布。

### 2. 模块级首次提交时间线

```bash
for f in $(git ls-files '*.py' '*.ts' '*.tsx' '*.yml' '*.json'); do
  echo "$(git log --diff-filter=A --date=short --pretty=format:'%ad' -- "$f" | tail -1) $f"
done | sort
```

逐模块列出"首次出现日期 + 引入该模块的提交"，用以说明每个模块都是随功能演进逐步加入的，而非从上游整体导入。

### 3. 代码量分布

```bash
git ls-files | xargs wc -l | sort -n
```

按目录给出代码量，说明自研模块的构成。

### 4. 与原型的差异说明

对每个被认为与开源项目相似的功能，写明：本项目要解决的问题 → 该模块为此做的设计取舍 → 与已知开源实现的差异（数据结构、算法、接口、部署形态）。

这一节的证据来自代码本身与提交历史，**不来自事后回忆**。

### 5. 第三方组件披露

指向 `THIRD_PARTY_NOTICES.md`（由 `code-provenance-audit` 生成），说明哪些是引用的上游配置/规则/看板及其许可证。

### 6. 待决与风险

列出：LICENSE 是否已定、是否有疑似逐字片段待重写或署名、比对工具的口径问题（函数粒度、不做标识符归一化）及其对读数的影响。

## 收尾

1. 把该文档与 `THIRD_PARTY_NOTICES.md`、重构后的比对结果一起提交，构成完整材料。
2. 在文档末尾注明生成命令与生成日期，使审查方可自行复现每一项事实。

## 不要做的事

- 不要用重构（`reduce-code-similarity-by-refactor`）的提交去"制造"原创性——重构只能消除误判，不能改变模块的来源与首次提交时间；材料里如实写成"为消除比对工具误判所做的实现重写"即可。
- 不要在文档里给出无法复现的命令或数字；每个数字都要能由文档中列出的 git 命令重新得出。
